1. Introduction

1.1 Purpose

This Software Requirements Specification describes the functional and non-functional requirements of CareConnect, a web-based Electronic Health Record (EHR) system that connects patients with their care providers. It is written for the project guide and evaluators, the developers who build and maintain the system, and the testers who verify it. The document is the reference for design, implementation, testing and acceptance of the system.

1.2 Scope

CareConnect supports the day-to-day work of an outpatient clinic. It lets receptionists register patients and book appointments, doctors document visits and place orders, nurses record vitals and administer medicines, pharmacists verify and dispense prescriptions, administrators manage users and master data, and patients view their own records online.

In scope: patient registration and history, clinical notes (SOAP), vital signs, ICD-10 diagnoses, computerized provider order entry (CPOE) with clinical decision support (CDS), laboratory results, e-prescribing, pharmacy verification and dispensing, drug inventory, medication administration record (MAR), appointment scheduling, patient portal with PDF downloads, secure messaging, notifications, dashboards and audit logging.

Out of scope: billing and insurance claims, inpatient bed management, integration with external laboratory or pharmacy systems (HL7/FHIR), real video calls for telehealth, and SMS/e-mail delivery.

2. Overall Description

2.1 Product Perspective

CareConnect is a new, self-contained system built as a three-tier web application. A single-page Angular application runs in the browser and talks to a Spring Boot REST API over HTTPS using JSON. The API stores all data in an Oracle database and uploaded documents on the server file system.

2.2 Product Functions

  • Register patients, generate MRNs and maintain allergies, problems, immunizations, family history and documents.
  • Record encounters with SOAP notes, e-signature, addenda, ICD-10 diagnoses and vital signs with trend charts.
  • Place lab, imaging, medication and referral orders with automatic allergy, interaction and duplicate checks.
  • Enter and flag laboratory results against normal and critical ranges.
  • Route e-prescriptions to the pharmacist for verification and dispensing with automatic stock deduction.
  • Record every medication dose on the MAR.
  • Manage provider slots and appointments, including online booking by patients.
  • Give patients a portal with their medicines, results, visit summaries (PDF), bookings and messages.
  • Provide role dashboards, in-app notifications, user and master-data administration, and a complete audit trail.

2.4 Operating Environment

  • Client: any modern browser (Chrome, Edge, Firefox, Safari) on desktop, tablet or phone.
  • Server: Java 17 or later; Windows or Linux; minimum 2 GB RAM.
  • Database: Oracle Database (tested with Oracle XE; later versions supported) on port 1521.
  • Build tools: Maven (wrapper included) and Node.js 20+ with npm.

2.5 Design and Implementation Constraints

  • Backend: Java 17+, Spring Boot 3.x (Web, Data JPA, Security, Validation), Maven, Lombok, MapStruct.
  • Frontend: Angular 17+ with standalone components, reactive forms, guards, interceptors and Angular Material.
  • Database: Oracle only, using sequences for keys, CHECK/unique/foreign-key constraints and indexes; schema changes via Liquibase.
  • Security: JWT access and refresh tokens, BCrypt password hashing, role-based access on both UI and API.
  • API documented with OpenAPI (Swagger UI); no secrets hard-coded – configuration through environment variables and profiles.

2.6 Assumptions and Dependencies

  • An Oracle database and a schema user with create-table/sequence rights are available before installation.
  • Drug, interaction, ICD-10 and lab reference data are loaded as master data and maintained by administrators/pharmacists.
  • Users access the system over a trusted network or HTTPS in production.
  • The system clock of the server is correct (appointments, audit and token expiry depend on it).

3. Functional Requirements

Priority: High = essential for release, Medium = important, Low = desirable.

3.1 Authentication and Access Control

IDRequirementPriority
FR-01The system shall authenticate users with username and password and issue a short-lived access token (15 min) and a refresh token (7 days).High
FR-02The system shall store passwords only as BCrypt hashes and give the same generic error for unknown user and wrong password.High
FR-03The system shall rotate the refresh token on each use and revoke all sessions of a user when a used token is presented again.High
FR-04The system shall restrict every screen and API operation to the roles allowed for it (Appendix A); disallowed calls return HTTP 403.High
FR-05The client shall renew an expired access token automatically and redirect to login when the session cannot be renewed.Medium
FR-06Users shall be able to change their own password (8–72 characters with a letter and a digit) and log out.Medium

3.2 Patient Records

IDRequirementPriority
FR-07Receptionists and doctors shall register patients with name, date of birth, gender, phone, address, emergency contact and insurance; the system shall generate a unique MRN.High
FR-08Staff shall search patients by name, MRN, date of birth or phone with paged and sortable results.High
FR-09Doctors and nurses shall maintain allergies (allergen, type, reaction, severity, status), immunizations and family history; doctors shall maintain the problem list with ICD-10 codes.High
FR-10Authorised staff shall upload clinical documents (PDF, images, up to 10 MB) with a category, and download them.Medium
FR-11The patient chart shall show a banner with identity and active allergies, and a summary of active problems, current medicines, latest vitals and open encounters.High
FR-12Updates shall be rejected when the record was changed by another user since it was loaded (optimistic locking).Medium
FR-13Administrators shall delete patient records by soft delete only; deleted records are hidden but retained for audit.Medium

3.3 Clinical Documentation

IDRequirementPriority
FR-14Doctors and nurses shall open an encounter (type, chief complaint, responsible doctor), optionally linked to an appointment.High
FR-15Doctors shall write SOAP notes, optionally starting from a template; a note is saved as DRAFT and only its author may edit it.High
FR-16Signing a note shall lock it permanently; corrections shall be added as signed addenda linked to the original note.High
FR-17Doctors shall add ICD-10 diagnoses to an encounter with type-ahead search; only one diagnosis may be PRIMARY.High
FR-18Doctors and nurses shall record vital signs (BP, pulse, temperature, respiratory rate, SpO2, weight, height); the system shall reject implausible values and calculate BMI.High
FR-19The system shall display vital sign trends as a chart and table.Medium
FR-20An encounter can be closed only when all its notes are signed; closed encounters accept no new notes or orders.High

3.4 Order Entry (CPOE) and Clinical Decision Support

IDRequirementPriority
FR-21Doctors shall place lab, imaging, medication and referral orders on an open encounter with priority (routine, urgent, STAT); each order receives a number ORD-NNNNNN.High
FR-22Before a medication order is placed, the system shall check it against the patient's active drug allergies (by drug name, generic name and class) and raise a CRITICAL alert on a match.High
FR-23The system shall check new medicines against the patient's active medicines using the interaction table: MINOR = info, MODERATE = warning, MAJOR = critical, CONTRAINDICATED = hard stop.High
FR-24The system shall warn about duplicate orders (same active drug or same pending test).High
FR-25Warning and critical alerts shall require an override reason; contraindicated combinations cannot be overridden. Alerts and reasons shall be stored with the order.High
FR-26Orders shall follow the lifecycle DRAFT → PLACED → IN_PROGRESS → COMPLETED, or CANCELLED with a reason; backward moves are not allowed.High
FR-27Doctors and nurses shall enter results; numeric lab values shall be flagged NORMAL, LOW, HIGH, CRITICAL_LOW or CRITICAL_HIGH against the test's ranges, and the ordering doctor notified.High

3.5 Medication Management

IDRequirementPriority
FR-28A medication order shall create an e-prescription (RX-NNNNNN) with dose, route, frequency, duration and quantity in status PENDING_VERIFICATION, and notify pharmacists.High
FR-29Pharmacists shall see the prescription with its CDS alerts, override reason, patient allergies and current stock, and verify it or reject it with a reason.High
FR-30Only verified prescriptions can be dispensed; dispensing shall reduce stock, write an inventory ledger entry and complete the order. Dispensing more than the available stock shall be refused.High
FR-31When stock reaches the reorder level the system shall list the drug as low stock and notify pharmacists.Medium
FR-32Pharmacists and administrators shall maintain the drug formulary, receive or adjust stock, and maintain drug-drug interactions.Medium
FR-33Nurses shall document each dose on the MAR as GIVEN, HELD, REFUSED or MISSED; a reason is mandatory for all except GIVEN.High
FR-34Doctors shall discontinue a medicine with a reason, or modify it (the old prescription is discontinued and a replacement goes back for verification).Medium

4. External Interface Requirements

4.1 User Interfaces

  • Public landing page describing the product, and a login page with show/hide password.
  • After login: side navigation filtered by role, top bar with role badge, notification bell and user menu.
  • Consistent Material Design components; tables with paging; dialogs for data entry; colour-coded status chips (e.g. red for critical).
  • Confirmation dialogs before irreversible or safety-relevant actions (sign, verify, dispense, cancel, delete, override).
  • Validation messages next to each form field; responsive layout down to 360 px width.

4.2 Software Interfaces

  • REST API over HTTP(S) with JSON bodies, documented with OpenAPI 3 (Swagger UI at /swagger-ui.html); 122 endpoints.
  • Oracle Database through JDBC (Oracle thin driver) and JPA/Hibernate.
  • Uniform error response: status, error code, message, field errors and details (e.g. CDS alerts).

4.3 Communication Interfaces

  • HTTPS in production; header Authorization: Bearer <token> on every protected request.
  • Cross-origin requests allowed only from configured front-end origins (CORS).

5. Non-Functional Requirements

IDCategoryRequirement
NFR-01SecurityAll API endpoints except login and token refresh require a valid JWT; role checks are enforced on the server with @PreAuthorize, and mirrored by route guards in the UI.
NFR-02SecurityPasswords are hashed with BCrypt; refresh tokens are stored only as SHA-256 hashes; secrets (DB password, JWT key) come from environment variables, never from source code.
NFR-03Privacy"Minimum necessary" access: e.g. receptionists see demographics but not clinical data; patients can reach only their own record (other records return 404).
NFR-04AuditabilityAudit entries are written in a separate transaction so they are kept even when the business operation fails.
NFR-05PerformanceTypical API responses complete within 1 second for up to 50 concurrent users; list screens are paginated (default 20 rows) and search columns are indexed.
NFR-06ReliabilityEach business operation runs in a database transaction; optimistic locking prevents lost updates; database constraints guarantee that stock never becomes negative.
NFR-07Data retentionClinical records are never physically deleted by users (soft delete); signed notes are immutable.
NFR-08UsabilityA new user can complete a core task (e.g. book an appointment) without training; all actions give success/error feedback; forms validate inputs before submission.
NFR-09PortabilityRuns on Windows and Linux; front end works in current versions of major browsers and on mobile screens.
NFR-10MaintainabilityLayered, modular code (controller / service / repository / DTO / mapper per module); database changes only through versioned Liquibase scripts; separate dev, test and prod profiles.
NFR-11TestabilityAutomated unit and integration tests (JUnit 5, Mockito, MockMvc) run without an Oracle installation using an in-memory database in Oracle mode.
NFR-12AvailabilityThe system is stateless on the server side, so it can be restarted or scaled without losing user sessions.

6. Data Requirements

All data is stored in the Oracle schema CARECONNECT. Primary keys are generated from one sequence per table; business numbers use dedicated sequences (mrn_seq, order_no_seq, rx_no_seq). Every transactional table carries created_at/by, updated_at/by and a version column.

GroupTables
Users and securitydepartments, app_users, refresh_tokens, audit_logs
Patient recordpatients, patient_allergies, patient_problems, immunizations, family_history, patient_documents
Clinicalencounters, clinical_notes, encounter_diagnoses, vitals, icd10_codes, note_templates
Orders and resultsclinical_orders, order_alerts, lab_tests, lab_results
Medicationdrugs, drug_interactions, prescriptions, medication_administrations, inventory_transactions
Scheduling and communicationprovider_slots, appointments, messages, notifications

Key integrity rules: unique MRN, username, order number and prescription number; CHECK constraints on all status and enumeration columns (gender, role, order status, severity, etc.); stock_qty >= 0; one lab result per order; one prescription per medication order; one portal account per patient; foreign keys between all related tables and indexes on every foreign key and search column.

Master data delivered with the system: 10 departments, about 40 ICD-10 codes, 16 lab tests with normal and critical ranges, 26 drugs, 17 drug interactions and 4 SOAP note templates.

7. Use Case Descriptions

UC-01: Place a medication order with decision support

ActorDoctor
PreconditionDoctor is logged in; the patient has an open encounter.
Main flow1. Doctor opens the encounter and selects New order → Medication.
2. Doctor searches and selects a drug; the system runs CDS checks immediately.
3. Doctor enters dose, route, frequency, duration and quantity.
4. If there are no alerts, doctor clicks Place order; the system saves the order and the e-prescription and notifies pharmacists.
Alternate flow3a. An allergy, interaction or duplicate alert is shown. The doctor either cancels, or enters an override reason and places the order; the alert and reason are stored.
3b. The combination is contraindicated: the order is blocked and cannot be placed.
PostconditionOrder is PLACED; prescription is PENDING_VERIFICATION.

UC-02: Verify and dispense a prescription

ActorPharmacist
PreconditionA prescription is pending verification.
Main flow1. Pharmacist opens the verification queue and selects a prescription.
2. System shows details, CDS alerts with override reason, patient allergies and stock.
3. Pharmacist verifies (optional note) and confirms.
4. From the dispense queue, pharmacist confirms the quantity; the system deducts stock, writes the ledger and completes the order.
Alternate flow3a. Pharmacist rejects with a reason; the prescriber is notified.
4a. Stock is insufficient: dispensing is refused with an error message.
4b. Stock falls to reorder level: pharmacists receive a low-stock notification.

UC-03: Document a visit

ActorsNurse, Doctor
Main flow1. Receptionist checks in the patient; doctor starts the visit from the appointment.
2. Nurse records vitals; BMI is calculated.
3. Doctor writes a SOAP note from a template and adds ICD-10 diagnoses.
4. Doctor signs the note (confirmation) and closes the encounter.
Exception4a. An unsigned note exists: closing is refused until all notes are signed.
Later corrections are made through signed addenda.

UC-04: Patient books an appointment online

ActorPatient
Main flow1. Patient opens My appointments, selects a doctor and date.
2. System shows free future slots.
3. Patient picks a time, chooses in-person or telehealth, enters a reason and confirms.
4. System books the slot (via PORTAL) and shows it under upcoming appointments.
Exception3a. Another user booked the slot meanwhile: the system reports that the slot is taken.
Patient may cancel own booking later with a reason.

UC-05: Login and session renewal

ActorAny user
Main flow1. User enters username and password.
2. System validates credentials, records the login and returns tokens.
3. User is taken to the role dashboard.
4. When the access token expires, the client obtains a new pair with the refresh token and repeats the request transparently.
Exception2a. Wrong credentials: generic error, failed login audited.
4a. Refresh token expired or revoked: user is returned to the login page.
